# Intake, kitchen helper and leftovers

## Implemented

- Receipt photo capture/library selection reuses the existing photo permission and storage components. OCR uses the installed optional native text extractor. The receipt screen reports unavailable OCR and permits typed/pasted lines without pretending recognition succeeded.
- Each receipt line requires catalog matching, explicit positive quantity/unit/storage and optional expiry review. Saving uses the existing BackendAddFoodStore, exact decimal validation and retry idempotency. No receipt or photo creates stock automatically.
- Receipt and food photos upload through the backend's real presigned PUT/confirm workflow. Household and user context are checked before upload and confirmation. Raw bytes, actual MIME type and the backend 10 MB limit are validated. Uploaded images are shown in a household-only archive with refreshed signed URLs. The archive is separate from stock, because the existing stock schema has no image relation.
- Kitchen helper reads all inventory pages and up to twelve server recipe details. It ranks recipes by matching required food IDs against positive stock whose entered dates have not passed and can explain dated food, storage contents and missing ingredients. It explicitly labels its rules-powered mode and does not claim to be an LLM, food-safety certification or medical advisor.
- Leftovers have a new household backend table and GraphQL module, guarded by authentication, active household membership and row-level security. Users can save cooked meals, portions, cooked date, optional reminder date, storage and notes; mark eaten/discarded; and restore a mistaken status update. Client-generated UUID saves are idempotent and conflicting payloads are rejected.
- Leftover reminders are user-entered dates, not inferred safe-until dates. The tracker is separate from ingredient stock and nutrition logging.
- Contact saves feedback in the independent backend with author/household row-level security and idempotent saves. Users can read their twenty latest submissions. It explicitly says saving is not email delivery. Contact writes no external messages automatically. With EXPO_PUBLIC_SUPPORT_EMAIL configured, it opens the user's email composer. Otherwise it exports feedback through the native share sheet. No fabricated support address or delivery confirmation.
- Community is routed to the backend feature agent's real household members/invitations interface. There is no public social network claim.

## Integration

Parent imports LeftoversModule into backend AppModule and applies migration 0029_cookbook_leftovers.sql to the isolated database only. Module also imports MediaModule for cookbookImages.

Default screen exports:

- `/receipt`: src/screens/intake-receipt-screen.tsx
- Photos feature: src/screens/intake-photos-screen.tsx
- Chat/helper feature: src/screens/assistant-screen.tsx
- Leftovers feature: src/screens/leftovers-screen.tsx
- Contact feature: src/screens/contact-screen.tsx
- Community: ConnectedHouseholdScreen from connected-household-screen.tsx

IntakeShell requires a signed-in account and gives loading/sign-in states. User-specific child components remount at identity changes. Shared API requests assert identity and household revision before returning data.
